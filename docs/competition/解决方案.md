## 第一章 项目概述

### 1.1 项目背景

HarmonyOS NEXT 自 2024 年发布以来，国产操作系统进入全场景设备一体化的快速发展期。截至 2026 年，OpenHarmony 生态已覆盖手机、平板、PC、手表、车机等多端场景，**应用数量与日活设备正以月均超过两位数百分比的速率增长**，与之配套的应用质量保障需求正在迅速凸显。应用厂商在 HarmonyOS NEXT 上的首次适配通常意味着需要重建一整套测试体系（功能、UI、兼容性、安全、性能），而**专门面向 OpenHarmony 应用的多模态智能测试工具长期缺位**——既有方案要么停留在脚本编写阶段，要么仅在 Android/iOS 生态下积累，跨生态适配成本与门槛居高不下。

在这样的产业背景下，**华为在 2026 年企业命题中专门设立「面向 OpenHarmony 应用的多模态智能测试系统」（u-a24）**，表达了对基于多模态 AI 的智能测试范式以及与现有鸿蒙测试体系深度融合的明确期待。本项目即围绕该命题开展研究、开发和产业化探索。

### 1.2 项目定位

本项目聚焦于**「让 OpenHarmony 应用测试从"写脚本验证已知路径"走向"看场景自动探索与缺陷发现"」**，构建一套具备以下能力的智能测试系统：

1. **多模态驱动的测试用例自动生成**：从自然语言需求文档、UI 设计稿、应用现有截图等多源数据自动生成可执行的 Hypium 测试脚本；
2. **真机/模拟器上的脚本执行与回放**：基于 `hdc` 与官方 Hypium 框架，对生成脚本进行真机调度执行，并支持用例库重放；
3. **缺陷的智能识别、分类与严重度评估**：融合应用层视觉、应用内部日志、设备系统日志等多模态信息，自动识别功能缺陷、UI 缺陷、兼容性缺陷、可达性问题、可访问性缺陷等多类问题，并按严重程度分级；
4. **缺陷知识沉淀与持续学习**：将历史缺陷结构化沉淀为可复用的缺陷知识库，驱动后续用例生成的策略优化与新缺陷的快速匹配。

系统以「**本地测试 Agent + Web 控制台**」形态实现，并已构建命题所鼓励的**闭环能力**——控制台以八阶段流水线串联全流程，与命题要求的"应用截图/布局采集 → 页面理解 → 交互路径规划 → 脚本生成 → 自动执行 → 结果分析 → 用例沉淀"逐环节对应（对照见附件 1.3）：

```
采集  →  感知  →  规划  →  探索  →  验证  →  脚本  →  回放  →  报告
Collect  Perceive  Plan   Explore  Verify   Script   Replay   Report
```

## 第二章 行业现状与痛点分析

### 2.1 OpenHarmony 生态对测试提出的新挑战

OpenHarmony 的全场景分布式特性，使其对测试工具提出了**不同于 Android/iOS 的新要求**：

| 维度 | Android/iOS 测试体系 | OpenHarmony 测试体系 |
| --- | --- | --- |
| 系统版本碎片化 | 高（厂商定制） | 中（统一 OS + 设备型号碎片） |
| 多端适配 | 双端（手机/平板/PC） | 多端（手机/平板/PC/手表/车机/智慧屏） |
| 控件识别 | 成熟生态（uiautomator/XCUITest） | 较新（arkUI/ArkTS 控件体系） |
| 跨设备流转 | 无 | 强需求（应用跨设备"流转"是核心能力） |
| 适配工具成熟度 | 高 | 低-中（工具尚在迭代中） |

这意味着，**直接复用 Android 多模态测试方案的迁移成本本身就要远超"端口适配"工作量**，必须在用例生成、设备调度、缺陷分析等核心环节做深度重构。

### 2.2 现有解决方案的三大共性短板

围绕鸿蒙应用测试，团队对截至 2026 年的代表性方案做了系统梳理：

1. **Hypium + DevEco Testing（华为官方）**：原生控件识别能力强，与 IDE 集成度高，但是**测试脚本仍需测试工程师人工编写**，每次 UI 改动都需要维护，对"我要测什么"和"该怎么测"的智能化完全留给人工。
2. **HmTest（SUSTech，2025，JCST 论文已发表）**：基于 ArkTS 静态分析 + 强化学习的探索式测试框架，在 9 个真实应用上验证了页面和语句覆盖率超越官方 wukong 和 DevEco Testing，**但是研究原型——没有用例自动生成、没有缺陷多分类分析、没有工程化平台**。
3. **HACMony（社区开源，2025）**：将 LLM 驱动的探索引入鸿蒙测试，专注音频流冲突（Hopping-related Audio-stream Conflict）一类硬件相关缺陷的检测，**覆盖面较窄，仅能检测一类缺陷**，且对功能/UI/安全等其他缺陷类型无覆盖。

三种方案各自解决了其中一环，但都**没有**同时具备下列能力：
- 多模态输入驱动测试用例自动生成；
- 多类缺陷（功能/UI/兼容/性能/安全/可达）的智能识别与分类；
- 缺陷的结构化沉淀、知识库与持续学习；
- Web 可视化、工程化的测试运营平台。

### 2.3 本项目的切入点

基于上述调研，团队将本项目的核心技术目标确定为：**在 OpenHarmony/HarmonyOS NEXT 生态下，构建业内首个"多模态驱动 + 真机执行 + 多类缺陷分析 + 缺陷沉淀闭环"的端到端智能测试系统**，完成鸿蒙应用测试从「自动化脚本执行」到「智能化探索与发现」的范式升级，并优先针对企业命题要求中的功能、可达性、可访问性三类典型场景落地验证。

## 第三章 总体技术方案

### 3.1 设计理念

系统在设计时遵循以下原则：

- **端到端闭环**：从需求到缺陷归档全链路打通，避免"半智能"方案中各模块割裂的问题；
- **多模态融合**：文本、图像、设备状态码、控制流数据等多模态信息在同一推理框架下协同决策；
- **原生兼容**：测试执行层尽量复用 Hypium + `hdc` 等官方能力，避免另起炉灶带来的生态碎片化；
- **持续学习**：将历史缺陷与历史用例结构化沉淀，使每一次测试运行都成为下一次更聪明测试的素材。

### 3.2 总体架构

本系统的总体架构划分为五大核心层与一个支撑平台：

```
┌─────────────────────────────────────────────────────────────┐
│                Web 可视化平台（Web Visualization）             │
│      测试任务管理 / 设备调度 / 报告中心 / 缺陷知识库          │
└─────────────────────────────────────────────────────────────┘
                              ▲
┌─────────────────────────────────────────────────────────────┐
│                缺陷智能分析层（Defect Intelligence）           │
│   功能缺陷诊断 · UI/视觉缺陷 · 兼容性缺陷 · 可达性分析        │
│   可访问性评估 · 严重度评分 · 缺陷分类归档 · 知识库写入       │
└─────────────────────────────────────────────────────────────┘
                              ▲
┌─────────────────────────────────────────────────────────────┐
│                真机执行层（On-device Execution）              │
│   Hypium 调度 · hdc 通信 · 多设备集群 · 录屏与日志           │
└─────────────────────────────────────────────────────────────┘
                              ▲
┌─────────────────────────────────────────────────────────────┐
│                智能用例生成层（Test Case Generation）         │
│   多模态 Prompt 构造 · 探索式 Agent · 用例评审与改写         │
└─────────────────────────────────────────────────────────────┘
                              ▲
┌─────────────────────────────────────────────────────────────┐
│              多模态理解层（Multimodal Perception）           │
│   UI 截图理解 · 控件树解析 · 应用日志 · 设备状态              │
└─────────────────────────────────────────────────────────────┘
```

五大功能层配合一个支撑平台（即"L1 实施基础"层），共同构成系统的整体闭环。

#### 3.2.1 实际落地架构（代码级 · 仓库已开源）

上述五层为概念分层。系统在仓库中的实际落地结构如下（`https://github.com/HIUEETR/oh-test-agent`）：

```
CLI / FastAPI / React 控制台
            ↓
     AgentOrchestrator（编排器）
       ├─ Planning + Vision + ToolDecision     （Pydantic AI）
       ├─ SafetyPolicy + ToolExecutor          （安全策略 + 工具白名单）
       ├─ HarmonyDeviceAdapter                 （类型化 HDC 适配器）
       ├─ PerceptionService                    （UI 层级 + VLM 融合）
       ├─ PageGraphBuilder                     （页面关系图构建）
       ├─ ArtifactStore + RunRepository        （证据存储 + 运行记录）
       └─ HypiumGenerator + HypiumRunner       （确定性脚本生成 + 回放）
```

**已在代码中固化的三条关键设计**：

1. **双模型分工**：`AGENT_MODEL` 负责任务规划，`AGENT_VISION_MODEL` 负责截图理解与逐步决策；后者留空时自动复用前者，因此**一个同时支持图像输入与结构化输出的模型即可覆盖全流程**；
2. **无模型间对话**：三个阶段通过 `PlanResult` / `ScreenSnapshot` / `ToolDecision` 三个数据结构通信，**模型之间没有直接聊天**——编排器始终是计划、页面状态与运行证据的唯一权威；
3. **可复盘的 Run Trace**：每次运行冻结当次的目标与 Profile 快照，**历史 Run 重新生成时不会读取后来变化的全局 Profile**，保证结果可复现、可追溯。

## 第四章 关键模块详解

### 4.1 多模态理解层

**职责**：把"被测应用当前长什么样 + 内部在做什么"转化为结构化的多模态状态。

**输入**：
- 设备屏幕截图（PNG/JPEG，720p-1440p）；
- 控件层级树（Hypium `dump_hierarchy()` 输出）；
- 应用当前 Activity/Page 元信息；
- 设备实时日志流（`hdc hilog`）；
- 测试人员提供的需求文档与 UI 设计稿（PNG/PDF/Markdown）。

**输出**：结构化的 UI Scene 对象，包含元素类型、坐标、文本、状态、以及语义级功能猜测。

**关键设计点**：
1. **截图分辨率自适应**：无论何种设备截屏，都先归一化为标准 1280×720（保持长宽比），便于模型推理；
2. **控件树-截图双轨融合**：仅靠截图理解会出现"图标含义错误"，仅靠控件树会丢失"该按钮当前是否被遮挡"，因此采用「控件树 + 截图 + 后处理一致性校验」三步融合；
3. **轻量视觉与重决策分离**：模型只做"看见+语义理解"，决策层使用大模型做下一步动作推荐；
4. **离线优先 + 在线增强**：若检测到设备网络不可用，将自动切换到本地轻量视觉模型；联网时调用 Qwen-VL / GPT-4o 级多模态模型以提高语义识别准确率。

### 4.2 智能用例生成层

**职责**：从需求文档、UI 设计稿与历史用例等来源，**自动生成可在 Hypium 中执行的标准测试脚本**。

**核心流程**：

1. **需求解析**：对 PRD 文档进行语义切片，识别其中的"用户场景 + 前置条件 + 操作步骤 + 预期结果"四元组；
2. **场景脚本化**：将每个场景转为自然语言描述，并标注涉及到的页面、关键控件、关键操作；
3. **多模态 Prompt 构造**：用 UI Scene 对象作为"页面状态"的精确描述，配合"我是测试工程师，应如何自动化这个场景"的指令，调用大模型；
4. **Hypium 脚本生成**：模型输出严格遵循 Hypium `pytest` 风格的 Python 代码（含 `UIDriver().find_component().click()` 等标准调用）；
5. **静态校验 + 动态验证**：先用 Python AST 解析生成脚本进行静态校验（确保无语法错误、关键 API 名拼写无误），再在沙箱中"干跑"一次（连接一台空载设备、点击空白页，验证脚本骨架无误）；
6. **回灌训练集**：被评审通过或被驳回的脚本都会被回灌到训练数据集，用于后续 Prompt 与模型微调。

**关键设计点**：
1. **结构化反射 + 多轮 CoT**：先让模型输出一份"伪代码"式的步骤清单，再迭代成 Hypium 代码，避免直接生成代码时出现"虚构 API"；
2. **可执行性自检**：每条生成的用例都附带一段"模拟执行"步骤，系统自动判断"该用例若执行，最可能在第几步卡住"，卡住的步骤会触发重新生成；
3. **支持场景多样性**：既支持"正向路径"也支持"反向路径"（如异常输入、网络中断），还支持"数据驱动"（同一逻辑不同数据）。

### 4.3 真机执行层

**职责**：在真实设备或模拟器上稳定执行生成的测试脚本。

**实现要点**：

1. **以 Hypium 为执行底座**：直接调用官方提供的 `UIDriver`、`By.id`、`By.text`、`By.image` 等核心 API，最大限度复用华为在鸿蒙测试上的投入。
2. **`hdc` 多设备集群**：通过自研 `DeviceFarm` 抽象，统一管理 hdc 连接、重连、设备状态变更监听；支持同步调度、多设备并行执行；
3. **失败回放与录屏**：每次执行均产出三份原始素材——**完整日志（`.log`）、关键节点截图（`.png`）、端到端录屏（`.mp4`）**——为后续缺陷分析提供证据链；
4. **用例库重放**：生成的"有效用例"入库后，支持后续单独重放某一用例（无须重新走完整流程），便于回归与回归失败定位；
5. **崩溃自愈**：当遇到 application crash、device offline、test framework error 时，自动重启测试设备上的测试引擎，跳过当前失败用例继续后续用例，确保测试不会因单点失败中断。

### 4.4 缺陷智能分析层

**职责**：对单次执行的产物做"是不是缺陷、是什么缺陷、多严重"的判断。

**支持识别的缺陷类型**：

| 缺陷类型 | 识别手段 | 严重度示例 |
| --- | --- | --- |
| 功能缺陷 | 用例脚本预期结果 vs 实际结果对比 | 严重：登录失败未提示 |
| UI 缺陷（布局/缺失元素） | 截图+控件树，对照设计稿 | 一般：按钮文本截断 |
| 兼容性缺陷 | 多设备对比：同一脚本不同设备行为差异 | 高：某机型下应用闪退 |
| 可达性缺陷 | 模型引导的智能遍历，识别"功能藏在 N 层菜单后的入口" | 中：用户场景无法触达 |
| 可访问性缺陷 | UI 组件 `accessibilityLabel` 检查 + 控件尺寸与点击区域 | 高：核心按钮无障碍属性缺失 |
| 性能问题 | 启动时间、帧率、内存占比 | 中：首页加载 > 5s |
| 崩溃/ANR | `hdc hilog` 中的异常栈匹配 | 严重：app crash |

**关键技术**：

- **期望-实际双校验**：基于"用例语义 + 截图 + 控件树"三模态融合，自动生成"这条用例本应发生什么"的语义描述，然后比对"实际发生了什么"，判断是否一致；
- **小样本分类**：对于无法预定义的缺陷类型，开放"用户上传若干个反例样本 → 模型快速微调 → 部署新分类"的工具链；
- **严重度评分**：综合"对用户的实际影响范围"+"触发概率"+"修复成本"，给出 0-100 的严重度分值，并自动给出 P0/P1/P2 建议分级。

### 4.5 缺陷沉淀与持续学习层

**职责**：让系统在多次测试运行之间"越来越聪明"。

**核心数据结构**：

- **缺陷模式库**：以"缺陷语义指纹 + 复现用例 + 修复建议"为单位持续追加；
- **用例执行日志**：每次执行的结果沉淀为可比对的时序数据；
- **生成用例的知识图谱**：哪些用例 → 触发了哪些缺陷 → 这些缺陷如何被修复，反哺用例生成策略。

**关键能力**：

1. **检索增强生成（RAG）**：在生成新用例前，先查缺陷模式库"过去类似场景踩过哪些坑"，让生成的用例"先避开已知雷区"；
2. **缺陷去重**：当团队再度发现"功能未提示"的同类缺陷时，系统会主动提示"该缺陷 2026-09-XX 在 X 用例中曾被发现，是否为回归？"，避免反复报告同一缺陷；
3. **缺陷趋势分析**：以看板形式呈现"按周新增、按类型分布、按严重度分布"，辅助质量管理决策。

### 4.6 支撑平台（Web 可视化与设备调度）

为方便测试工程师、QA Lead、PM 三类角色使用，提供 Web 化平台，核心模块：

- **测试任务管理**：上传需求文档 → 生成用例 → 配置设备 → 启动执行；
- **设备调度中心**：查看所有可用真机/模拟器的状态、应用在线情况、最近一次测试设备；
- **报告中心**：缺陷列表、用例执行结果、回归趋势、设备适配矩阵；
- **缺陷知识库**：检索、批量标注、版本绑定、与 Jira/TAPD 等研发协作平台对接。

控制台于 2026-09 完成一次彻底重写，最终收敛为 **5 个页签**——**会话 / 页面关系图 / 脚本与回放 / Profile 资产 / 历史运行**，实时展示大模型的规划、视觉理解、逐步决策与探索顾问的对话留痕，并配有闭环流水线状态条。旧版控制台冻结在 `web-legacy/` 作为备份，不再继续演进。

### 4.7 安全边界与受控执行（已落地）

系统在实现上坚持一条核心原则：**模型负责理解与选择，不负责任意执行**。Agent 不持有通用 Shell 能力，所有设备操作都必须经过类型化适配器与安全策略层。

**Agent 工具白名单（12 个，代码级封闭）**：

| 工具 | 用途 | 工具 | 用途 |
| --- | --- | --- | --- |
| `inspect_screen` | 读取当前屏幕与控件层级 | `swipe` | 滑动 |
| `open_app` | 启动指定应用 | `back` | 返回 |
| `click_element` | 按语义定位器点击 | `wait` | 等待 |
| `click_coordinate` | 坐标兜底点击（显式告警） | `assert_visible` | 断言元素可见 |
| `input_text` | 文本输入 | `assert_not_visible` | 断言元素不可见 |
| `finish` | 结束任务 | `assert_text` | 断言文本内容 |

**默认禁止的高危操作**：登录、支付、验证码、删除、卸载、清除数据、授权。
**探索期的额外约束**：提交、发布、下载需**逐项显式启用**；支付、删除、卸载、清除数据**始终禁止**。

**失败语义不伪装**：模型失败返回 `failed_model`、设备失败返回 `failed_device`、元素缺失返回 `failed_element`、断言失败返回 `failed_assertion`——不会伪装为成功，也不会在失败后继续执行后续危险动作。

**执行期安全约束**：HDC 只能经类型化 Adapter 使用；坐标、超时和危险语义在执行前校验；**每轮最多执行一个工具**；失败、断言失败、设备断开与连续无页面变化均立即停止。

### 4.8 探索治理机制（防过度探索 · 已落地）

自动探索最大的工程风险是"越探越偏、误触信息流、把同一页面反复当成新页面"。系统为此设计了四层治理：

1. **逻辑页身份去重**：页面按 `page_path + 前台应用 + 全量折叠 key + 可交互结构` 联合判定身份。信息流／热搜这类"同一页面、不同内容"的抖动不再被误判为新页面；
2. **内容候选抑制**：`key`/`id` 中内嵌长数字 ID、或标题超长的可点击元素被降级到输入与滑动之后，避免主动误触信息流卡片进入不可回放的内容页；此类跃迁不入队；
3. **类型配额**：每页动作预算按类型分配（`click ≤ max-2`、`input 1`、`swipe 1`），使"点击富集型"页面也能覆盖输入与滑动两类交互；
4. **分级恢复节奏**：候选动作之间优先"落地页身份校验 → 一次 `back` → 冷启动重放"逐级兜底（输入类动作因软键盘强制冷恢复），只有队列出队回放路径才必须冷启动。

此外，在配置视觉模型后默认开启 **LLM 视觉探索顾问**：每个新逻辑页向一段连续会话追加一次"截图 + 候选"询问，模型返回"推荐／回避"建议用于对确定性候选列表重排过滤；安全分类器在顾问之后照常执行，顾问调用失败自动回退启发式排序，不阻塞主流程。探索默认上限为 **20 个页面 / 每页 8 个动作 / 15 分钟**。

## 第五章 创新点

### 5.1 创新点一：鸿蒙原生需求-用例端到端自动生成

**问题**：当前 OpenHarmony 应用测试用例生成严重依赖人工编写，需求文档到可执行 Hypium 脚本之间存在工程化鸿沟。现有 Hypium 官方工具不提供自动化生成能力，而 HmTest/HACMony 等学术方案仅在「文本输入生成」等局部环节做探索，未覆盖需求全链路。

**创新实现**：
- 提出"PRD → 场景四元组 → 多模态 Prompt → Hypium 脚本"四阶段流水线；
- 设计一种"结构化反射 + 多轮 CoT"的代码生成策略，先让大模型输出伪代码步骤，再迭代收敛到可在 Hypium 真实运行的 Python 脚本；
- 内置 Hypium API 知识库（如 `UIDriver().find_component()`、`By.id`/`By.text`/`By.image` 等）在 Prompt 中作为约束输入，从源头降低模型幻觉；
- 在生成—验证—回灌闭环中持续学习，使生成用例的实际可执行率从初版约 60% 提升至目标 90%。

**实测已达成的成果**：单次运行即可从一条自然语言目标产出 **17 个语义定位器 + 9 个断言 + 完整可执行 Hypium 脚本**；脚本库已累计 28 个脚本 / 10 条录制流，并具备 `Live`（可直接回放）质量标记；页面关系图自动构建 5 个状态节点，使应用结构可被复用而非每次从零探索。

**后续量化目标**：相对人工编写，单条用例编写成本下降 60% 以上；用例场景覆盖率从典型项目 75% 提升至 95%；新需求响应周期的"测试交付"阶段从 3–5 天缩短至 1 天。

### 5.2 创新点二：多类缺陷的统一智能分析与严重度评估

**问题**：现有鸿蒙测试工具（Hypium/wukong）只能报告"测试失败"，需要人工介入才能判定失败原因；HmTest 偏向覆盖率；HACMony 仅专项音频流缺陷，没有覆盖功能/UI/兼容/可达/性能/可访问性等多类型。

**创新实现**：
- 提出"六类缺陷（功能/UI/兼容/可达/可访问性/性能）+ 崩溃/ANR"统一的智能识别框架，使单一系统能同时覆盖企业在鸿蒙应用上的常见质量诉求；
- 设计"期望-实际双校验"机制：先用多模态大模型从用例语义层推断"该用例执行后，应用应当处于什么状态"，再在执行后用同一套多模态模型判定"实际所见是什么状态"，两者差分即缺陷候选；
- 严重度评分由"对用户的影响范围 + 触发概率 + 修复成本"三个维度加权得出，并自动给出 P0/P1/P2 建议分级；
- 引入"小样本分类器"机制：当企业遇到自定义缺陷类型（例如某业务专属的"工单流转丢失"），可通过上传 5-10 个反例样本，模型快速微调并部署为新分类。

**实测已达成的成果**：已自动识别「点击后页面未发生跳转，疑似无响应控件」类缺陷（`defect-acd239b4d353`），并同步完成崩溃/白屏/异常退出的排查（`collect_logs` 检查 SUSPECTED CRASH，实测无命中）；每个缺陷自动绑定影响面（应用 / 页面 / 触发动作 / 设备）、触发统计（累计 9 次）、证据链（6 张截图）与 finding 明细（7 条）。七类缺陷框架中，**「页面无响应」「崩溃/ANR」两类已完成端到端实测验证**，其余类别随 L2 迭代逐步上线（详见 §7.4）。

**后续量化目标**：缺陷识别准确率（人工复核后）≥ 85%；严重度判定一致性（与资深测试工程师对比）≥ 80%。

### 5.3 创新点三：缺陷沉淀驱动的持续学习机制

**问题**：测试工具一旦在历史用例历史缺陷上"踩坑"过，再次遇到同类问题时却无法记住；现有方案在跑完就丢，未形成可持续运营的"质量数据资产"。

**创新实现**：
- 设计"缺陷语义指纹"作为沉淀单元，结构化记录触发场景、复现条件、设备类型、修复建议等关键要素；
- 引入 RAG 检索增强，在新用例生成阶段主动调阅缺陷知识库，避免重蹈覆辙；
- 缺陷去重与回归检测：当团队再度发现疑似同类缺陷时，系统会主动给出"该缺陷早前曾被报告"提示；
- 趋势看板：按时间/类型/严重度多维度呈现缺陷演变，使质量数据成为可被业务、研发共同消费的"产品"。

**实测已达成的成果**：缺陷归并机制已实际生效——同一缺陷 `defect-acd239b4d353` 在 2026-09-23 01:07:25 首次发现后，于 2026-09-24 04:04:27 再次运行时被**自动归并为同一编号**（而非报告为两条新缺陷），并累计触发次数至 9 次；Profile 资产复用机制使已沉淀的 16 个定位器在后续运行中可直接加载（增量模式）。

**后续量化目标**：重复缺陷的报告率从典型项目 25% 下降至 <5%；缺陷知识库在 3 个月内积累 ≥ 300 条结构化缺陷指纹；RAG 辅助用例生成上线后，同类场景的首次探索步数下降 30% 以上。

### 6.2 与 Hypium + DevEco Testing（华为官方）的互补定位

Hypium 是 OpenHarmony 测试体系的"基石"，本项目并非取代 Hypium，而是**与 Hypium 共生**：
- **Hypium 之上**：本项目的真机执行层完全基于 Hypium 6.x 实现，复用其在原生控件识别上的精度优势；
- **Hypium 之侧**：本项目提供 Hypium 缺少的"用例自动生成"、"缺陷智能分析"、"缺陷知识沉淀"等能力；
- **Hypium 之沿**：本项目所有产物可一键导出为 Hypium 标准脚本，企业可在不切换工具栈的前提下使用。

### 6.3 与 HmTest 的差异化

HmTest 已在 JCST 2025 发表并开源，是目前鸿蒙测试智能化的代表性研究。本项目的差异化主要在以下三点：
1. **目标函数不同**：HmTest 优化目标是"最大化语句/页面覆盖率"，是研究视角；本项目目标是"端到端智能化使能 + 产业化运营"，强调工程闭环；
2. **能力覆盖面更广**：HmTest 不做用例自动生成，也不做缺陷分类与沉淀；本项目覆盖这两块；
3. **平台化交付**：HmTest 是 CLI 工具；本项目是 Web 平台，更贴近企业 QA 团队的日常协作习惯。

### 6.4 与 HACMony 的差异化

HACMony 是社区开源项目，聚焦"音频流冲突"一类硬件相关缺陷。本项目与之相比：
- **缺陷类型**超出音频，覆盖七类典型缺陷；
- **不限于单一生态**，既支持鸿蒙原生应用，也计划扩展到安卓/跨端；
- **平台化交付**，并具备缺陷沉淀机制。

**工程规范要点**：

- **确定性脚本生成**：Hypium Python 由固定模板产出，JSON 只写入已验证字段，**模型不能自由生成可执行代码**；
- **证据链完整**：每个 Action 关联前后 Snapshot、布局、SHA-256 与命令证据；截图必须落到本地；
- **运行产物不入 Git**：动态截图、布局 JSON、模型输出、日志、数据库均由 `.gitignore` 排除，仅保留目录契约；经筛选的稳定 fixture 放在 `tests/fixtures/`；
- **密钥不出仓库**：配置通过 `.env.example` 模板管理，真实 `.env` 不提交。

**一键复现路径**：

```
uv sync --all-groups
Copy-Item .env.example .env      # 填写模型 / VLM / HDC / 设备配置
uv run main.py preflight         # Python、依赖、模型、Hypium、HDC、设备、截图、布局八项预检
uv run main.py dev --install     # 同时启动 FastAPI 与 Vite 控制台
uv run main.py run --provider openai --task "<自然语言测试目标>"
uv run main.py generate --run-id <run-id>          # 从 Run Trace 重新生成 Hypium 脚本
uv run main.py execute --run-id <run-id> --attempts 3   # 回放 1—3 次
```
