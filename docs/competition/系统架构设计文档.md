# 系统架构设计文档

> 面向 OpenHarmony 应用的多模态 UI 测试代理与 Hypium 用例生成系统
>
> 本文档从**代码实现**出发描述系统架构，所有结论均可在源码中逐一对应（模块路径以 `src/harmony_test_agent/` 为根）。

## 1. 系统概述

本系统是一个面向 OpenHarmony（OH）应用的**多模态 UI 测试代理**，核心能力是：连接真机采集截图与控件层级 → 由大模型理解界面并决策 → 在设备上执行 UI 操作 → 将真实操作轨迹沉淀为可复用的**测试用例中间表示（Case IR）** → 从同一份 IR 渲染出两种可在设备上执行的脚本（独立 Hypium `UiDriver` 脚本、官方 `xdevice`/`devicetest` 工程）→ 执行后做只读的缺陷分析。

- **发行包名**：`mvp`；**导入包名**：`harmony_test_agent`；**命令行入口**：`harmony-test-agent = harmony_test_agent.cli:main`。
- **运行时**：Python ≥ 3.14。关键依赖：`fastapi`、`uvicorn`、`httpx`、`hypium==6.1.0.210`、`pydantic-ai==1.73.0`、`pydantic-settings`、`sqlmodel`、`jinja2`、`pillow`。
- **设备通道**：全部通过 `hdc`（OpenHarmony Device Connector）子进程完成，无私有协议。
- **被测样例应用**：知乎++（`zhihu-plus`，bundle `com.github.zhuoyi233.zhplus`，入口 `EntryAbility`），默认设备 `127.0.0.1:5555`。

系统提供两种彼此隔离的运行形态：

1. **自动流水线（Live Mode）**：由 `AgentOrchestrator`（`agents/orchestrator.py`）驱动的状态机，一次性完成「解析目标 → 有界探索/复验 → 规划 → 逐步执行 → 生成脚本 → 回放 → 沉淀资产」。
2. **直流交互模式（DC Mode）**：由 `DcSessionManager`（`dc/`）驱动的多轮 Agent 会话，人给自然语言目标、模型自主调用分层工具在设备上操作，会话轨迹同样可沉淀为用例与应用画像。

### 2.2 贯穿全局的设计原则（源自代码）

- **UI 层级是权威，视觉是补充**：`PerceptionService.merge` 以设备 `dumpLayout` 归一化后的元素为基线，只把达到置信度阈值（`vlm_min_confidence`，默认 0.55）且在屏幕边界内的视觉元素叠加进来。
- **分析永远是 advisory，绝不翻转结论**：`ExecutionAnalyzer` 与 `InRunDetector` 都只追加 `AnomalyFinding`，从不改变用例的 `passed`，也从不影响 Profile 晋级门禁（`analysis/service.py`、`analysis/in_run.py` 的共同红线）。
- **质量三轴解耦**：脚本「能不能跑（runnable）」「质量高不高（confidence）」「能不能作为应用画像晋级证据（promotion-eligible）」是三个相互独立的判定，见 §6。
- **录制与产出解耦**：真实操作先落成一份 `TestCaseSpec`（Case IR），脚本是 IR 的渲染结果；同一 IR 可同时渲染独立 Hypium 脚本与官方 xdevice 工程。
- **安全内建**：永久禁止动作（支付/删除/卸载/清数据）在探索、直流、静态门禁三处一致拦截；敏感动作（登录/授权/提交/发布/下载）默认关闭、需显式开启。
- **可复现产物落盘**：数据库只存 IR 本体与产物目录指针，脚本、xdevice 工程、报告、截图等大文本仍留在文件系统，便于审计与二次执行。

## 3. 自动流水线：`AgentOrchestrator` 状态机

`AgentOrchestrator.run()` 是自动形态的主循环，全程持续把事件、轨迹、报告写盘（`RunEventEmitter` + `RunRepository` + `ArtifactStore` + `ReportBuilder`）。运行状态由 `RunState` 枚举驱动：

```
CREATED
  └─ PREFLIGHT ─────────────── 连接设备 + health_check
        └─ RESOLVING_TARGET ── TargetResolver 按 app 名 / bundleName 解析唯一目标
              ├─（同名多候选）→ WAITING_TARGET_SELECTION → 等待用户选择后继续
              ├─（已有 verified 画像）→ PROFILE_REVALIDATING 快速复验
              │                            成功 → 直接复用；失败 → 转完整探索
              └─（无画像且开启探索）→ 完整 bootstrap：
                    PROBING_TARGET → DISCOVERING（BoundedExplorer）
                      → PROFILE_DRAFTING（保存 draft 画像）
                      → PROFILE_VERIFYING（ProfileVerifier 多轮重启回放）
                      → 准入门禁（≥3 定位器 / ≥3 页面状态 / ≥2 断言）
                      → SCRIPT_GENERATING（从验证证据生成门禁脚本）
                      → SCRIPT_EXECUTING（HypiumRunner 回放）
                      → PROFILE_PROMOTING（全部通过 → 晋级 verified）
        └─ 任务执行（非 bootstrap_only）：
              PLANNING（provider.plan 生成原子步骤）
                └─ EXECUTING ⇄ VERIFYING ⇄ GRAPH_UPDATING（逐步循环，见 §3.1）
                      └─ SCRIPT_GENERATING → （可选）SCRIPT_EXECUTING
                            └─ COMPLETED
  失败态：FAILED_MODEL / FAILED_ACTION / FAILED_DEVICE / FAILED_TARGET_RESOLUTION
          / FAILED_TARGET_PROBE / FAILED_DISCOVERY / FAILED_PROFILE_VERIFICATION
          / FAILED_SCRIPT / FAILED_PROFILE_PROMOTION / FAILED_ELEMENT / FAILED_ASSERTION
  中断态：STOPPED_BY_USER（每个安全检查点检查 request_stop）
```

**任务型运行默认不前置完整探索**（`BOOTSTRAP_ENABLED_ON_TASK_RUN`，`orchestrator.py`）：完整探索代价高（实测一次白烧约 8.8 分钟），因此默认进入「实时模式」直接执行任务，应用画像由任务期证据回收作为副产物累积；完整探索通过 `POST /api/profiles/{id}/verify`（`bootstrap_only=True`）显式触发。

### 3.1 观测 → 决策 → 执行循环

每个计划步骤 `PlannedStep` 走同一个循环（`_decide_and_execute`）：

1. **采集稳定帧**（`_capture_stable_frame`）：截图后轮询 UI 层级直到结构指纹稳定，过滤加载动画/过渡帧；预算耗尽时复用最后一次层级而非重复整条截图链路（动态页面每步最大单笔开销）。
2. **观测 + 决策**：真实 provider 支持「一次请求同时返回视觉观测与工具决策」（`supports_combined_observation`），每步因此只花 1 次视觉往返而非 2 次；mock 走确定性双调用路径。
3. **执行工具**：`ToolExecutor` 执行 12 种 `ToolName` 之一（见 §5.3），执行前经 `SafetyPolicy` 校验。
4. **验证 + 更新图**：采集动作后帧，登记断言结果，向 `PageGraphBuilder` 追加状态转移边。
5. **自适应恢复**：语义失败（`FAILED_ELEMENT`/`FAILED_ASSERTION`）不立即终止，而是把失败反馈交回模型并重新截屏，在 `agent_step_recovery_limit` 预算内重试；断言类步骤必须由模型重新发出断言且通过才算完成；靠恢复绕路完成的步骤记 `WorkaroundRecord` 以保证可见。
6. **健壮性护栏**：连续变更类动作后画面 SHA 不变累计到 `unchanged_screen_limit` 即判定卡死；模型调用超时/瞬时故障（429/5xx/网关）按退避重试，仍失败才归类 `FAILED_MODEL`。

## 4. 设备接入层：`HarmonyDeviceAdapter`

`devices/harmony.py` 把全部设备能力封装为 `hdc -t <device_id> <...>` 子进程调用，是系统与 OH 设备之间唯一的边界：

| 能力 | 底层命令 |
|---|---|
| 采集 UI 层级 | `uitest dumpLayout` → `cat` 读回 JSON 树 |
| 截图 | `snapshot_display` + 文件 `recv` 取回 PNG（与 dumpLayout 并行）；另有 `screenshot_jpeg` |
| 启动/停止应用 | `aa start -b <bundle> -a <ability> [-m <module>]` / `aa force-stop` |
| UI 操作 | `uitest uiInput`（点击/输入/滑动/返回），`_ui_input_result` 识别「退出码 0 但打印 usage」的假成功 |
| 应用信息 | `bm dump -a`（已安装列表）/ `bm dump -n <bundle>`（单应用清单） |
| 日志与内存 | `hilog -x`（日志导出）、`hidumper --mem`（内存采样，压力用例用） |
| 前台应用 | 解析当前前台 bundle/ability/window_type，用于跨应用跳转与崩溃判定 |

所有上层（编排器、探索器、执行器、分析器）都只依赖 `DeviceAdapter` 抽象，便于以 mock 设备做确定性单测。

## 5. 智能体与感知

### 5.1 层级归一化：`perception/normalizer.py`

`normalize_layout` 把 `dumpLayout` 的原始节点树深度遍历（`walk_nodes`）为统一的 `UIElement` 列表：

- 过滤不可见/禁用节点与系统节点前缀（`StatusBar`/`Battery`/`Clock`/`keyboard`/…）；
- 解析 `bounds`（`[l,t][r,b]`）为 `BoundingBox`，越界或退化矩形丢弃；
- 判定可交互性：`clickable`/`scrollable`/`editable`（`TextInput`/`Search`/`Input`/`TextArea` 或类型名含 `input`）；
- 为每个元素生成多个带分值的定位器候选：`KEY`=1.0、`ID`=0.98、`TEXT`=0.9、`TYPE_TEXT`=0.85；
- `element_id` 由 `key|id|text|type|index` 的 SHA1 派生，去重稳定。

`normalize_ui_text` 是**比较用**的文本归一化纯函数（全半角折叠、中文数字→阿拉伯、时间/日期统一形式、标点转空格、casefold），被断言求值与元素语义匹配（`find_element`）共用，一处修两处受益。

### 5.2 视觉合并：`perception/service.py`

`PerceptionService.merge` 以层级元素为基线，把 `VisionObservation` 中置信度达标、在屏内的视觉元素叠加进来：命中已有元素则取更高分、补内容与视觉理由；未命中则新增 `source="vlm"`、`LocatorKind.VLM_BBOX` 的元素。这解决了「软键盘、纯图标控件」在层级里缺失的问题（对应挑战目标「多模态理解截图+布局」）。

### 5.3 智能体 Provider：`agents/providers.py`

`AgentProvider` 抽象接口定义了 `plan`（规划原子步骤）、`analyze`（视觉观测）、`decide`（单步决策）、`observe_and_decide`（合并观测+决策）、`advise_turn`（探索顾问）、`plan_bug_repro`（缺陷复现规划）、`chat`（直流对话）七个能力：

- **`MockAgentProvider`**：本地确定性实现，无需模型，用于离线测试与 CI；
- **`OpenAICompatibleProvider`**：基于 `pydantic-ai`，走 OpenAI 兼容协议。关键工程决策：用 `PromptedOutput` 而非强制 tool 模式（思维链模型会拒绝被强制 `tool_choice`）；截图以 JPEG `BinaryContent` 上传；按分值只送 top-N 元素，控制上下文体积。
- **`create_provider`**：按 `agent_provider`（`auto`/`openai`/`mock`）与是否配置了模型端点自动选择实现。

自动流水线可用的 12 个 `ToolName`：`inspect_screen`、`open_app`、`click_element`、`click_coordinate`、`input_text`、`swipe`、`back`、`wait`、`assert_visible`、`assert_not_visible`、`assert_text`、`finish`。

### 5.4 有界自动探索：`discovery/explorer.py`

`BoundedExplorer` 在**页面数、单页动作数、时长、bundle 边界**四重约束内自动遍历应用，产出可用于构建 draft 画像的 `DiscoveryResult`（对应挑战目标「自动探索页面状态与流程图」）：

- **逻辑页身份**（`_structural_identity`）：`page_path + 前台 bundle/window_type + 折叠后的结构骨架 key + 可交互结构` 的 SHA256。key 折叠掉任意数字串并剔除内容流噪音（信息流卡片、`feed/card` 容器、时间/日期型 key），使「同一页面、不同推荐内容」收敛为同一逻辑页——这是知乎首页这类内容抖动剧烈的应用能被稳定去重的关键。
- **动作风险分级**（`ActionRiskClassifier`）：基于确定性 UI 文本判定为 `DEFAULT_ALLOWED` / `REQUIRES_OPT_IN` / `FORBIDDEN` / `BLOCKED_UNCERTAIN`，复用与静态门禁同一套安全词表。永久禁止与未开启的敏感动作只记录不执行。
- **类型均衡预算**（`_select_candidates`）：保证 input/swipe 动作在点击密集页也不被点击挤掉，让探索覆盖多种交互类型（准入要求 `min_interaction_kinds` ≥ 2）。
- **可选 LLM 顾问**（`ExplorationAdvisor`）：为每个逻辑页请求一次建议（同结构身份复用不重复请求），重排/过滤候选动作；顾问每轮输入输出都作为进度事件推送，供前端实时渲染。
- **代价递增的恢复**（`_recover_to_source`）：候选动作之间优先复用当前帧 → 连续 `back` → 最后才 `stop_app`+`start_app`+全路径重放。
- **崩溃与外链区分**（`_probe_crash_after_foreground_loss`）：前台丢失时立即采 hilog 尾部 + faultlog 索引；命中崩溃模式记为异常 finding，否则记为「跨应用导航被拦截」并恢复——修正了历史上「真崩溃被静默当作外链」的缺陷。
- **早停**（`_early_success`）：一条动作类型达标的路径覆盖 ≥3 个逻辑页即达准入指标，提前结束。

### 5.5 页面状态图：`graph/service.py`

`PageGraphBuilder` 把运行中采集到的每一帧计算页面签名（稳定 key + 归一化文本 + 8×8 平均哈希感知指纹），按签名去重为 `PageNode`，动作跳转记为 `PageEdge`（携带 `ToolName` 与目标）。最终 `graph.json` 即该次运行探索出的页面状态迁移图。

## 6. 质量三轴解耦（核心设计）

生成脚本 / 画像晋级不是单一「通过/不通过」，而是三个正交判定，分别落在 `GeneratedArtifact`（`models.py`）与 `cases/builder.py`：

| 轴 | 字段 | 判据 | 作用 |
|---|---|---|---|
| **可执行（runnable）** | `replay_eligible` / `runnable_blockers` | 纯物理：有可回放动作 + 应用身份非占位 | 决定脚本能否被 `HypiumRunner` 执行 |
| **置信度（confidence）** | `confidence` = high/medium/low + `confidence_factors` | 质量：是否有显式断言、是否 provisional/live_mode、结局是否完整 | 只影响「质量提示」，**不阻断**执行与入库 |
| **可晋级（promotion-eligible）** | `promotion_eligible` / `promotion_blockers` | 证据：是否有跨轮画像验证与跨会话定位器证据 | 决定能否作为应用画像晋级 verified 的证据 |

这一解耦的直接后果：`live_mode`/`provisional` 只是**质量信号**，脚本照常立即可执行、可入库、可手动回放（`POST /api/runs/{id}/execute` 只看 `replay_eligible`）；只有画像晋级链才严格要求跨轮验证证据。

## 7. 用例与生成层

### 7.1 Case IR：`TestCaseSpec`

`cases/spec.py` 的 `TestCaseSpec` 是「录制动作」与「产出脚本」之间的中间表示，把两者解耦。它包含 `case_id`（格式 `case-<UTC>-<6hex>`）、`slug`、`title_zh`、`scenario`、`status`（draft→active→archived）、`bundle_name`、`setup`/`steps`/`teardown`、可选的 `stress` / `bug_repro`、以及 `provenance`（来源溯源）。IR 由 7 条校验不变量保证自洽（详见《测试用例生成说明》）。四种构建来源（`CaseBuilder`）：Live 轨迹、DC 会话、压力请求、缺陷报告。

### 7.2 同一 IR，双执行引擎

`generation/` 从同一份 IR 渲染两种可在设备上执行的产物，两者共用定位器渲染（`selectors.py::render_selector`）与检查点渲染（`checkpoints.py`）：

- **`StandaloneEmitter`（`standalone.py`）**：独立的 Hypium `UiDriver` Python 脚本。契约：产出 `generated_result.json`（至少含 `run_id`/`passed`/`error`/`case_id`/`soft_failures`）；报告目录由环境变量 `HARMONY_AGENT_REPORT_DIR` 指定；落 `final.jpeg`/`failure.jpeg`；`setup` 走 stop→start→wait；主体 try/except/finally；压力循环内用 `hidumper --mem` 采样 PSS；数据驱动参数经 `HARMONY_AGENT_CASE_PARAMS` 注入 `param()`。
- **`XDeviceEmitter`（`xdevice_case.py`）**：官方 `xdevice`/`devicetest` 工程树（`testcases/HarmonyAgentCases/HarmonyAgentCase.py` + `testfile.json` + `testlist.txt` + `reports/` + `logs/`），使用 `devicetest.core.test_case` 的 `Step`/`CHECK`/`ASSERT`/`MESSAGE`/`TestCase`/`@loop`；生成后用 `compile()` 自检；文件名必须与类名一致。

`render_selector` 输出的定位器形态覆盖：`BY.key('v')`、`BY.key('prefix', MatchPattern.STARTS_WITH)`、`BY.text('v')`、`BY.text('v', MatchPattern.CONTAINS)`、`BY.type('T').text('x')`、以及坐标 `(x, y)` 兜底。

### 7.3 用例沉淀与复用：`CaseLibrary`

`cases/library.py` 的 `CaseLibrary` 负责把用例落盘并复用，磁盘布局 `artifacts/cases/<case_id>/v<N>/`（`case_spec.json`、`standalone/`、`xdevice/`、`hypium/attempt-XX/`、`executions/`）。它支持 `build_from_run`、`build_from_dc`、`execute`（引擎 `hypium_standalone` 走 `HypiumRunner.execute_diagnostic`，或 `xdevice_devicetest`），并在执行后按症状复现与否更新缺陷状态（缺陷 reconciliation）。用例版本在 `CaseRepository`（SQLite）中 `(case_id, version)` 不可变、内容去重。

## 8. 执行与分析层

### 8.1 隔离执行：`runner/hypium.py`

`HypiumRunner` 在隔离运行目录中执行具备回放资格的脚本：把子进程 `HOME`/`USERPROFILE`/报告目录限制到运行产物区；捕获超时；解析 `generated_result.json`；把资格拦截、进程退出码、脚本自报失败区分为 `ineligible`/`timed_out`/`invalid_result`/`failed`/`passed` 等结构化状态。`execute_diagnostic` 是「不计入画像晋级证据」的独立路径，供直流录制脚本与用例库重跑使用，可透传设备 SN 与数据驱动参数。可选挂 `analysis_hook`：分析失败只记日志，绝不改变回放结论。

### 8.2 事后分析：`analysis/service.py`

`ExecutionAnalyzer` 是一条 advisory 分析流水线，入口有 `analyze_replay` / `analyze_dc_script` / `analyze_run` / `analyze_xdevice`。它综合 faultlog + hilog、白屏帧扫描、无响应检测（超时标记或帧/树停滞两类独立信号）、定位器失效、布局异常、压力内存增长等，产出 `AnomalyFinding` 并写 `analysis.json`；`symptom_reproduced` 判定复现与否。**从不翻转 `passed`**。

### 8.3 运行中检测：`analysis/in_run.py`

`InRunDetector` 采用「**廉价门 → 昂贵取证**」策略，保证常态路径零额外设备调用：每个变更类动作（`MUTATING_TOOLS`）后，先做两次纯本地计算——整图 SHA 比较与**结构指纹**比较（结构指纹复用探索器语义，天然抗状态栏时钟/光标闪烁这类抖动）；两者都未命中即返回 `None`，一次设备调用都不发。命中可疑时才查前台应用 + 采 hilog/faultlog：前台丢失且命中崩溃模式 → 具体崩溃类型；前台丢失未命中 → `PAGE_UNRESPONSIVE(critical)`；结构停滞 → 首次 `warning`，累计到 `escalate_count` 个**不同动作**才升 `critical`。同样从不翻转 `passed`。

### 8.4 白屏与布局检测

`analysis/screen.py::detect_blank_screen` 用灰度降采样 + 裁剪后的**三重门**判定白屏：标准差 < 阈值（默认 8.0）**且** 空白像素占比 ≥ 0.97 **且** 均值分类为亮屏/暗屏/纯色。`detect_identical_frames` 检测连续相同帧。`analysis/layout.py` 从 dump 解析控件重叠/越界等布局异常。这些共同覆盖挑战目标「崩溃/卡死/白屏/无响应/布局异常」的缺陷检测。

### 8.5 缺陷一等产物：`analysis/defects.py`

`RunState` 的失败态全是 agent 视角，没有一个表示「被测应用有问题」。`DefectRecorder` 因此把 `AnomalyFinding` 归并、落库为跨运行持久的 `DefectRecord`：

- **归并键** `(bundle_name, kind, page_path, action_target)`：同一应用同一页面同一动作反复触发同类异常 → `occurrences += 1`、更新 `last_seen_at`，**不新增记录**；`occurrences` 即「偶现/必现」的证据强度。
- **稳定 id**（`stable_defect_id`）：由归并键派生，使「运行中发现」与「事后分析发现」的 finding 能按 id 去重合并。
- **生命周期** `DefectStatus`：`suspected` → `confirmed`（复现用例重跑 `symptom_reproduced=True`）/ `not_reproduced` / `dismissed`（人工判误报）。
- **缺陷 → 复现用例**（`defect_to_bug_repro_request`）：`ANOMALY_TO_SYMPTOM` 与 `cases/bug_repro.py::symptom_sentinel` 互为反函数，把缺陷回灌成可执行的复现用例，闭环「发现→复现→确认」。

## 9. 应用画像：`TargetAppProfile` 与 `ProfileRegistry`

`TargetAppProfile`（`models.py`，`schema_version=2`）是**版本化、可复用的应用测试资产**：稳定定位器清单、断言清单、核心流程、启动/复位/测试数据/权限策略。生命周期 `ProfileStatus`：`draft` → `candidate` → `verified`，另有 `superseded`/`invalid`/`absent`。

- **准入门禁**（`profiles/admission.py`，阈值来自 `config.py`）：`min_stable_locators=3`、`min_page_states=3`、`min_assertions=2`、`min_interaction_kinds=2`。
- **晋级链**：draft → 多轮重启验证（`ProfileVerifier`）→ candidate → 从验证证据生成门禁脚本 → `HypiumRunner` 回放 → 全部通过才 `promote` 为 verified。晋级证据只能来自画像验证脚本（`test_`/`dc_test_` 前缀），杜绝任意任务脚本冒充证据。
- **不变量**：画像永远不能启用 `clear_app_data`，也不能放行任何永久禁止动作。
- **复用**：已有 verified 画像时优先快速复验；draft/candidate 有定位器时进入增量模式复用并累加证据。
- **异步补充回放**：比赛「3 次连续成功」要求由主流程内联 1 次（`HYPIUM_REPLAY_ATTEMPTS`）+ 用户/CI 经 `POST /api/profiles/{id}/replay` 在设备空闲时追加 2 次，主流程不被阻塞。

`target_app_profile.json`（仓库内真实样例）即知乎++ 的 verified 画像：`aa start -b com.github.zhuoyi233.zhplus -a EntryAbility` 启动、stop-then-start 复位（`clear_app_data:false`）、匿名只读测试数据（`login:false`、固定关键词 `OpenHarmony`）、登录+验证码显式阻断。

## 10. 直流交互模式（DC Mode）

`dc/` 提供一套与自动流水线**在模型层完全隔离**的多轮 Agent 会话（`dc/models.py` 只引用 `CommandResult`/`ScreenSnapshot`/`UIElement`，不复用 Live 的 `EventType`/状态机）。用户给自然语言目标，模型在一轮内自主多次调用工具直到完成。

- **分层工具（26 个，5 级）**：`DcToolTier` L1 UI 交互（11：click/swipe/input_text/key_event/back/wait/screenshot/inspect_screen + 3 个断言）、L2 观测诊断与启动（7：dump_ui_hierarchy/collect_logs/foreground_app/list_apps/inspect_app/memory_dump/start_app）、L3 应用管理（4：force_stop/install/uninstall/clear_app_data）、L4 文件（3）、L5 受控 Shell（1）。高层级包含低层级；默认 L2。
- **副作用与对账**：有设备副作用的工具（`SIDE_EFFECT_TOOLS`）超时/取消后副作用未知，禁止自动重放；`DcContinuationContext` 只携带用户可见事实跨轮延续，隐藏思维链原文绝不进入下一轮上下文；未确认动作进入对账期，下一轮必须先重新观测。
- **预算与超时**：单轮工具调用预算、单轮总时长（`DC_TURN_TIMEOUT`）、单次模型调用超时（`AGENT_MODEL_TIMEOUT`）、请求/工具调用上限，均有专门异常类型（`DcTurnBudgetExceeded`/`DcTurnTimeout`/`DcModelTimeout`/`DcUsageLimitReached`）携带命中的上限值，便于提示「调大哪个环境变量后继续」。
- **可观测性**：会话内累计真实 token 用量与缓存命中率（`DcTokenUsage`，数值全部来自 provider 真实响应）；独立的 `DcEventType` SSE 事件流；会话状态落 `dc_session.json` 可从磁盘恢复。
- **沉淀**：会话轨迹经 `CaseBuilder.from_dc_invocations` 生成用例、经 `DcProfileDistiller` 蒸馏应用画像（复用探索器的结构身份重建核心流，校验 ≥3 页面覆盖）。运行中发现的异常同样收进 `defects` 并可转复现用例。

## 11. 安全设计

安全策略（`runtime/safety.py::SafetyPolicy` + `cases/safety.py::validate_case_spec`）在多处一致执行，`ExplorationPolicy`（`models.py`）定义三档动作权限：

- **默认允许**：`navigate`、`swipe`、`back`、`input_fixed_text`、`read_only_assertion`；
- **需显式开启**：`login`、`permission`、`submit`、`publish`、`download`（CLI `--allow-*` / API `exploration_policy`）；
- **永久禁止**：`payment`、`delete`、`uninstall`、`clear_data`——任何形态、任何配置都不放行。

其他护栏：凭据类文本（密码/验证码/OTP）需显式密钥引用，否则拦截；`KEY_EVENT` 仅白名单按键（Back/Home/Enter/VolumeUp/VolumeDown）；压力用例迭代数/时长/等待有上限；坐标定位器必须带边界并告警；循环体内禁止 `START_APP`/`STOP_APP`。静态门禁违规在压力/CLI 路径返回 HTTP 422，在 Live/DC 路径降级为 draft。测试数据默认匿名只读（不登录、固定关键词），从设计上避免污染真实账号或触发不可逆操作。

**网络暴露提示**：FastAPI 服务默认绑定 `127.0.0.1` 且未内建鉴权（`api/app.py` 仅配置 CORS）。若部署到非本机可达的地址，需自行在前置网关加访问控制——当前实现假定运行在可信本地环境。

## 12. 存储与产物布局

**SQLite（`artifacts/agent.db`，多仓库共用一库）**：

- `RunRepository`：运行轨迹 `RunTrace` 与事件流；
- `CaseRepository`：用例版本行（`(case_id, version)` 不可变、内容去重）、摘要与执行历史；
- `DefectRepository`：缺陷记录（按归并键查/存，带写锁保证 `occurrences` 不丢更新）。

数据库只存 IR 本体（`spec_json`）与产物目录指针（`artifact_dir`），**大文本产物留在文件系统**（`ArtifactStore`）：

```
artifacts/
├─ agent.db                         # 上述三仓库共用
├─ runs/<run_id>/                    # 单次运行产物
│   ├─ screens/  discovery/  verification/  commands/
│   ├─ graph.json                    # 页面状态图
│   ├─ hypium/attempt-XX/            # 回放证据（stdout/stderr/command/environment/generated_result）
│   └─ reports/report.html           # 运行报告
├─ cases/<case_id>/v<N>/             # 用例版本目录
│   ├─ case_spec.json  standalone/  xdevice/  hypium/attempt-XX/  executions/
├─ profiles/                         # 应用画像（draft/candidate/verified + history 备份）
└─ dc/<session_id>/                  # 直流会话（dc_session.json + 截图/脚本）
```

## 14. 技术选型与理由

| 选型 | 理由（源自代码约束） |
|---|---|
| `hdc` 子进程作唯一设备通道 | 无私有协议，贴合 OH 官方工具链；`HarmonyDeviceAdapter` 单点封装便于 mock 测试 |
| `hypium==6.1.0.210` + `xdevice`/`devicetest` | 同一 IR 双引擎产出，既有轻量独立脚本，又有官方工程可接入正式测试体系 |
| `pydantic-ai==1.73.0` | 统一 provider 抽象、结构化输出、图文多模态上传；`PromptedOutput` 规避思维链模型拒绝强制 tool_choice |
| `pydantic` 领域模型贯穿全栈 | 模型即契约（IR 不变量、画像不变量、事件 schema），序列化/校验/落库一致 |
| `SQLite` + 文件系统分离 | 结构化元数据入库、大文本产物留盘，兼顾查询与审计/二次执行 |
| `FastAPI` + SSE | 后台长任务 + 实时事件流；`asyncio.to_thread` 把阻塞的设备/子进程调用移出事件循环 |
| mock provider | 离线确定性测试，CI 无需真机与模型即可验证编排/生成/分析全链路 |
