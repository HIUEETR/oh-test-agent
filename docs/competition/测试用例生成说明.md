# 测试用例生成说明

> OpenHarmony 多模态 UI 测试代理 —— 从真机观测到可复用、可执行、带断言的测试用例
>
> 本说明从**代码实现**出发描述用例是如何生成的，所有结论均可在 `src/harmony_test_agent/` 下逐一对应。

## 1. 概述：用例生成的总链路

本系统的「用例生成」不是把模型输出直接拼成脚本，而是分三步：

```
真机观测/操作轨迹  ──►  Case IR（TestCaseSpec）  ──►  双引擎可执行脚本
（Live / DC / 压力 / 缺陷）   （录制与产出解耦的中间表示）   （独立 Hypium 脚本 + xdevice 工程）
                                     │
                                     ├─ 7 条不变量自校验（cases/spec.py）
                                     ├─ 静态安全门禁（cases/safety.py）
                                     └─ 沉淀入库、版本化、可复用（cases/library.py）
```

**核心思想**：先把「发生过什么操作、要验证什么」固化为一份结构化的 `TestCaseSpec`（Case IR），脚本只是这份 IR 的渲染结果。这样同一份 IR 可以：

- 同时渲染两种执行引擎（独立 Hypium `UiDriver` 脚本、官方 `xdevice`/`devicetest` 工程）；
- 携带明确的步骤、断言/检查点、setup/teardown；
- 版本化沉淀、内容去重、跨运行复用；
- 与缺陷记录互相转换（缺陷 → 复现用例）。

涉及模块：`cases/spec.py`（IR 定义）、`cases/builder.py`（四来源构建）、`cases/stress.py`（压力）、`cases/bug_repro.py`（缺陷复现）、`cases/safety.py`（安全门禁）、`cases/library.py`（沉淀复用）、`generation/`（脚本渲染）、`storage/case_repository.py`（落库）。

## 2. 用例中间表示：`TestCaseSpec`（Case IR）

`cases/spec.py::TestCaseSpec` 是用例的唯一权威表示，主要字段：

| 字段 | 含义 |
|---|---|
| `case_id` | 用例标识，格式 `case-<UTC 时间戳>-<6 位十六进制>` |
| `slug` / `title_zh` | 机器可读短名 / 中文标题 |
| `scenario` | 场景类型（`ScenarioKind`，见 §7） |
| `status` | 生命周期：`draft` → `active` → `archived` |
| `bundle_name` | 被测应用 bundle |
| `setup` | 前置步骤（`pre_steps`），默认 stop→start→wait |
| `steps` | 主体步骤序列（每步一个 `StepAction` + 可选定位器 + 检查点） |
| `teardown` | 后置步骤（`post_steps`） |
| `stress` | 压力规格（`StressSpec`，仅压力场景） |
| `bug_repro` | 缺陷复现规格（`BugReproSpec`，仅复现场景） |
| `provenance` | 来源溯源（`source_kind`/`source_id`/关联画像等） |
| `tags` | 标签，用于检索 |

## 3. 四种用例来源：`CaseBuilder`

`cases/builder.py::CaseBuilder` 提供四个构建入口，把不同来源的原始轨迹统一转成 `TestCaseSpec`：

| 方法 | 来源 | 场景 |
|---|---|---|
| `from_trace` | 自动流水线（Live）执行的 `RunTrace` 真实动作序列 | core_flow / smoke / exploratory |
| `from_dc_invocations` | 直流会话（DC）录制的工具调用序列 `DcToolInvocation` | core_flow（可蒸馏画像） |
| `from_stress_request` | 压力请求（`StressRequest`） | stress |
| `from_bug_repro` | 缺陷报告（`BugReproRequest` → `BugReproPlan`） | bug_reproduction |

四者产出的都是同构的 `TestCaseSpec`，因此下游生成、执行、沉淀、分析路径完全一致——这是「录制与产出解耦」带来的直接收益：新增一种录制来源，只需实现一个 builder，不触碰生成与执行。

**from_trace / from_dc_invocations** 会把每个真实动作映射为一个 `Step`：动作类型 → `StepAction`，命中的元素 → 定位器（见 §5），动作后的断言 → 检查点（见 §6）。**from_stress_request** 与 **from_bug_repro** 走各自的专用构建逻辑（§8、§9）。

## 4. 控件识别与动作映射

### 4.1 控件如何被识别

控件识别发生在感知层 `perception/normalizer.py::normalize_layout`：把 `hdc uitest dumpLayout` 的原始节点树归一为 `UIElement`，并标注可交互性：

- `clickable`：节点 `clickable == "true"`；
- `editable`：类型为 `TextInput`/`Search`/`Input`/`TextArea`，或类型名含 `input`；
- `scrollable`：节点 `scrollable == "true"`；
- `selected`：用于区分同页不同 Tab 的选中态。

每个元素带上按分值排序的定位器候选（`KEY`=1.0 / `ID`=0.98 / `TEXT`=0.9 / `TYPE_TEXT`=0.85），供后续定位器决策使用。软键盘、纯图标等层级里缺失的控件由视觉观测补充（`PerceptionService.merge`）。

### 4.2 动作映射：17 个 `StepAction`

Case IR 的步骤动作枚举 `StepAction`（`cases/spec.py`）共 17 个，覆盖比赛要求的全部控件交互类型：

| 比赛控件类型 | 对应 `StepAction` |
|---|---|
| 按钮点击 | `click`（另有 `double_click`、`long_click`） |
| 文本输入 | `input_text`（配 `clear_text` 清空） |
| 列表滑动 | `swipe`（另有 `drag`、`fling`） |
| 页面返回 | `back` |
| Tab 切换 | `click` / `switch_status`（切换选中态） |
| 弹窗确认 | `click`（命中弹窗按钮） |
| 其他 | `key_event`（白名单按键）、`wait`、`screenshot`、`start_app`、`stop_app`、`check`（断言）、`noop_comment`（注释占位） |

自动流水线运行时用的是 12 个 `ToolName`（`inspect_screen`/`open_app`/`click_element`/`click_coordinate`/`input_text`/`swipe`/`back`/`wait`/`assert_visible`/`assert_not_visible`/`assert_text`/`finish`）；这些运行期工具在落成 IR 时被规整为上表的 `StepAction`。

## 5. 定位器策略：`LocatorSpec` 与 `locator_from_candidate`

### 5.1 定位器表示：`LocatorSpec` + `MatchMode`

Case IR 用 `LocatorSpec` 表示「如何在设备上找到一个控件」：定位方式（`key`/`id`/`text`/`type_text`/`coordinate`）、定位值、匹配模式 `MatchMode`（`equals` / `contains` / `starts_with` / `ends_with` / `regexp`），坐标定位还带边界信息。

### 5.2 从候选到定位器：`locator_from_candidate`

`cases/builder.py::locator_from_candidate` 决定把感知到的元素落成哪种定位器，核心是**抗动态化**：

- **动态 key 泛化**：key 命中 `(.+?[_-])\d{8,}`（前缀 + 长数字串，典型如带实例 ID 的信息流控件）时，若有跨轮画像证据、或时间戳前缀在采集帧中唯一，则退化为 `STARTS_WITH` 前缀匹配（`BY.key('prefix', MatchPattern.STARTS_WITH)`），避免把一次性实例 ID 写死进脚本。
- **易变 key 剔除**：`is_unreplayable_locator_key` 判定为不可回放的易变 key → 返回 `None`，改用坐标兜底或直接省略。
- **文本兜底**：无稳定 key/id 时退到 `BY.text` 文本定位。

这套策略让生成的脚本在「同一页面、不同推荐内容」的场景下仍能稳定命中控件——对知乎++ 这类内容抖动剧烈的应用尤为关键。

### 5.3 定位器渲染：`generation/selectors.py::render_selector`

两种引擎共用同一个 `render_selector`，输出的 Hypium/xdevice 定位器形态：

| IR 定位方式 | 渲染结果 |
|---|---|
| key（精确） | `BY.key('value')` |
| key（前缀） | `BY.key('prefix', MatchPattern.STARTS_WITH)` |
| text（精确） | `BY.text('value')` |
| text（包含） | `BY.text('value', MatchPattern.CONTAINS)` |
| type + text | `BY.type('Type').text('value')` |
| 坐标兜底 | `(x, y)` |

## 6. 断言与检查点

### 6.1 检查点类型：9 个 `CheckpointKind`

一份高质量用例必须带明确的「验证点」。IR 中每个步骤可挂检查点，类型枚举 `CheckpointKind`（`cases/spec.py`）：

| CheckpointKind | 验证内容 |
|---|---|
| `element_exists` / `element_absent` | 目标控件存在 / 不存在 |
| `text_equals` / `text_contains` | 文本精确相等 / 包含 |
| `property_equals` | 控件属性等于期望值 |
| `toast` | 出现指定 toast（要求提前 `listen_toast`） |
| `current_app` | 当前前台应用为期望 bundle（崩溃/闪退检验） |
| `page_signature` | 页面结构签名命中锚点（白屏/跳错页检验） |
| `screenshot_captured` | 成功截图（取证用） |

### 6.2 硬检查点 vs 软检查点

- **硬检查点**：失败即用例失败。IR 不变量要求「非 draft 用例至少含 1 个硬检查点」，杜绝「跑完但什么都没验证」的空用例。
- **软检查点**：失败不改变 `passed`，只作提示。在独立脚本里落进 `generated_result.json` 的 `soft_failures`；在 devicetest 工程里渲染为 `CHECK` + `MESSAGE`（而非 `ASSERT`）。

### 6.3 检查点渲染：`generation/checkpoints.py`

`render_standalone_checkpoint` 与 `render_devicetest_checkpoint` 把检查点映射到具体 Hypium API：`check_component` / `check_component_exist` / `get_component_property` / `check_toast` / `current_app` / `capture_screen` / `switch_component_status`；硬断言只用 `hypium.checker.assertion` 里的 `Assert`。文本类断言在求值前统一走 `normalize_ui_text`（全半角、中文数字、时间/日期归一），使「下午1:00」与屏幕上的「下午01:00」判为一致。

## 7. 场景类型：`ScenarioKind`

Case IR 的 `scenario` 字段标注用例属于哪类测试场景（`models.py::ScenarioKind`），覆盖并超出比赛要求的「≥2 种场景」：

| ScenarioKind | 含义 | 构建来源 |
|---|---|---|
| `core_flow` | 核心流程回归 | Live 轨迹 / DC 会话 |
| `bug_reproduction` | 缺陷复现 | 缺陷报告（§9） |
| `exploratory` | 探索性测试 | Live 轨迹（探索路径） |
| `stress` | 压力/稳定性 | 压力请求（§8） |
| `smoke` | 冒烟（启动、可达页面、返回、重启恢复） | Live 轨迹 |

除 `bug_reproduction` 改变 Live 执行路径（走专用规划器）外，其余场景只作为标签透传给 IR，不改变执行链路。

## 8. 压力测试用例生成：`cases/stress.py`

`StressRequest` 经 `build_stress_case` 生成压力用例。压力类型枚举 `StressKind` 共 4 种，各自的循环体构造不同：

| StressKind | 循环体 | 说明 |
|---|---|---|
| `repeat_click` | 单次点击 | 对同一控件反复点击 |
| `continuous_swipe` | 上滑 + 下滑成对 | 列表连续滚动 |
| `page_enter_exit` | 进入（核心流）+ `BACK` × N | 页面反复进出 |
| `soak` | 来自既有用例 / 内联步骤 / 核心流 | 长时间浸泡，**必须**给 `duration_budget` |

关键机制：

- **逐轮检查点**（`per_iteration_checkpoints`）：每次迭代后校验应用仍存活/页面仍正常，能在第几轮出问题上定位；
- **超时公式**：`timeout = min(7200, max(300, 60 + iterations*5 + budget))`，随迭代数与浸泡预算自适应，且封顶 7200 秒；
- **内存采样**：独立脚本压力循环内用 `hidumper --mem` 采样 PSS，供事后内存增长分析（`AnomalyKind.MEMORY_GROWTH`）；
- **共享构建**：`steps_from_exploration_actions` 与编排器共用，把探索动作转成压力循环体；
- **安全边界**：迭代数、时长、单次等待都有上限（见 §11），且循环体内禁止 `START_APP`/`STOP_APP`。

## 9. 缺陷复现用例生成：`cases/bug_repro.py`

自然语言缺陷描述经 `BugReproRequest` → `BugReproPlan` → `TestCaseSpec` 三步转成可执行的复现用例（对应挑战目标「自然语言缺陷复现」）：

- **输入 `BugReproRequest`**：标题、症状 `symptom`、症状类型 `symptom_kind`（`crash`/`freeze`/`unresponsive`/`white_screen`/`layout`/`functional`/`other`）、前置条件、自然语言复现步骤 `repro_steps_nl`、期望 `expected`、实际 `actual`、目标应用。
- **规划**：真实 provider 走 `plan_bug_repro`，离线用 `mock_bug_repro_plan`（确定性），把自然语言步骤规整为原子步骤。
- **症状哨兵**（`symptom_sentinel`）：按症状类型自动补一个**判定缺陷是否复现**的检查点：

| symptom_kind | 哨兵检查点 |
|---|---|
| `crash` | `current_app`（应用是否还在前台） |
| `white_screen` / `layout` | `page_signature`（页面结构是否异常） |
| `freeze` / `unresponsive` | `element_exists` + 8 秒等待 |
| `functional` | `text_contains` |

- **语义反转**：复现用例的 **「通过（pass）= 缺陷未复现」**。即脚本成功跑到底且哨兵未触发，说明缺陷已修复/无法复现；哨兵触发则用例失败，代表缺陷确实存在。这与缺陷记录的 `symptom_reproduced` 判定互逆（`analysis/defects.py::ANOMALY_TO_SYMPTOM` 与 `symptom_sentinel` 互为反函数，有单测钉住）。

**闭环**：`ExecutionAnalyzer`/`InRunDetector` 发现的 `AnomalyFinding` → 归并成 `DefectRecord` → `defect_to_bug_repro_request` 回灌成复现用例 → 重跑确认（`suspected` → `confirmed`/`not_reproduced`），形成「发现 → 复现 → 确认」闭环。

## 10. IR 校验不变量（7 条）

`TestCaseSpec` 在构建时自校验 7 条不变量，任何一条不满足都拒绝落库，保证生成的用例结构自洽、可执行、有验证力：

1. **压力对称**：`scenario == stress` ⟺ 存在 `stress` 规格（有其一必有其二）；
2. **复现完整**：`scenario == bug_reproduction` ⟹ 存在 `bug_repro` 规格；
3. **步骤合法**：非压力用例至少 1 个步骤，且步骤序号严格为 `1..N` 连续；
4. **参数存在**：数据驱动中被引用的 `param_ref` 必须在参数表中已定义；
5. **验证非空**：非 draft 用例至少含 1 个硬检查点（不允许「跑完不验证」）；
6. **toast 前提**：含 `toast` 检查点 ⟹ 必须已开启 `listen_toast`；
7. **锚点非空**：`current_app` 检查点的 `expected` 非空 / `page_signature` 检查点的 `anchors` 非空。

## 11. 静态安全门禁：`cases/safety.py::validate_case_spec`

用例落库前经静态安全校验，与探索、直流复用同一套 `runtime.safety.SafetyPolicy` 词表：

- **永久禁止**：动作文本命中 `payment`/`delete`/`uninstall`/`clear_data` → 拒绝；
- **凭据保护**：命中密码/验证码/OTP 类文本需显式密钥引用；
- **按键白名单**：`KEY_EVENT` 仅允许 `Back`/`Home`/`Enter`/`VolumeUp`/`VolumeDown`；
- **压力边界**：迭代数 ≤ 上限（`stress_max_iterations`，默认 2000）、时长 ≤ 7200 秒、单次等待 ≤ 30 秒；
- **坐标约束**：坐标定位器必须带边界并告警（坐标随分辨率漂移）；
- **循环体约束**：循环体内禁止 `START_APP`/`STOP_APP`。

违规处理分路径：压力/CLI 路径直接返回 **HTTP 422** 拒绝；Live/DC 录制路径**降级为 draft**（保留证据但不作为正式可执行用例）。

## 12. 生成产物：同一 IR，双执行引擎

`generation/` 从同一份 `TestCaseSpec` 渲染两种设备可执行产物，二者共用 `render_selector`（§5.3）与检查点渲染（§6.3）：

### 12.1 独立 Hypium 脚本：`StandaloneEmitter`

完整的 `UiDriver` Python 脚本，产出契约：

- 写 `generated_result.json`，**至少**含 `run_id`、`passed`（bool）、`error`、`case_id`、`soft_failures`；
- 报告目录由环境变量 `HARMONY_AGENT_REPORT_DIR` 指定；落 `final.jpeg`（结束帧）与 `failure.jpeg`（失败帧）；
- `setup` 走 stop → start → wait；主体包在 try/except/finally 中；
- 压力循环内用 `hidumper --mem` 采样 PSS；
- 数据驱动参数经环境变量 `HARMONY_AGENT_CASE_PARAMS` 注入 `param()`，设备选择经 `HARMONY_AGENT_DEVICE_SN`。

### 12.2 官方 xdevice 工程：`XDeviceEmitter`

标准 `xdevice`/`devicetest` 工程树：

```
xdevice/
├─ testcases/HarmonyAgentCases/HarmonyAgentCase.py   # 文件名必须 == 类名
├─ testfile.json
├─ testlist.txt
├─ reports/
└─ logs/
```

使用 `devicetest.core.test_case` 的 `Step`/`CHECK`/`ASSERT`/`MESSAGE`/`TestCase`/`@loop`：计数型压力用 `@loop` 装饰器，SOAK/内存类用显式 for 循环；生成后用 `compile()` 自检语法。硬检查点渲染为 `ASSERT`，软检查点渲染为 `CHECK` + `MESSAGE`。

### 12.3 隔离执行：`runner/hypium.py`

`HypiumRunner` 在隔离目录执行脚本（`HOME`/报告目录都限制在运行产物区），解析 `generated_result.json`，把结果结构化为 `passed`/`failed`/`timed_out`/`invalid_result`/`ineligible`。用例库重跑走 `execute_diagnostic`（不计入画像晋级证据）。

## 13. 用例沉淀与复用：`CaseLibrary` + `CaseRepository`

生成的用例通过 `cases/library.py::CaseLibrary` 落盘并复用：

- **磁盘布局**：`artifacts/cases/<case_id>/v<N>/`，内含 `case_spec.json`、`standalone/`（独立脚本）、`xdevice/`（工程）、`hypium/attempt-XX/`（执行证据）、`executions/`（执行历史）；
- **入口**：`build_from_run`（从 Live 运行沉淀）、`build_from_dc`（从直流会话沉淀）、`execute`（引擎 `hypium_standalone` 或 `xdevice_devicetest`）；
- **版本化落库**：`storage/case_repository.py::CaseRepository`（SQLite，与运行/缺陷仓库共用 `agent.db`）。`(case_id, version)` 行不可变，任何内容/状态变更都追加新版本；与最新版本内容完全相同则**复用已有版本号**（内容去重，同一来源重复生成不灌水版本号）；
- **执行历史**：每次执行记为 `CaseExecutionRecord`（引擎、设备、通过与否、报告路径、分析结果、错误）；
- **缺陷 reconciliation**：执行后按症状是否复现更新关联缺陷状态。

## 14. 生成脚本的质量分级（三轴）

每个生成产物（`GeneratedArtifact` / `DcScriptArtifact`）带三个正交判定，三者互不阻断：

| 轴 | 字段 | 判据 |
|---|---|---|
| **可执行** | `replay_eligible` / `runnable_blockers` | 纯物理：有可回放动作 + 应用身份非占位 |
| **置信度** | `confidence`（high/medium/low）/ `confidence_factors` | 质量：有无显式断言、是否 provisional/live_mode、结局是否完整 |
| **可晋级** | `promotion_eligible` / `promotion_blockers` | 能否作为应用画像晋级证据（需跨轮验证 + 跨会话定位器证据） |

`evaluate_runnable`（两条物理条件）、`evaluate_confidence`（high/medium/low）、`_promotion_blockers`（provisional/live_mode 等）均在 `cases/builder.py`。关键后果：**质量不合格不代表不能跑**——`confidence=low` 的脚本照样可执行、可入库、可手动回放，只有画像晋级链才严格要求证据。

## 15. 端到端示例（知乎++ 搜索流程）
